The idea

Anyone who has kept a garden knows the problem, since everything ripens at once and you end up with far more tomatoes than you can eat, while the neighbor two streets over has the same problem with figs. Share Crops started as my concept for a UX design project at UMGC, where I did the user research, wireframes and storyboards for a community garden app built around trading rather than selling, and I liked the idea enough to keep building it after the class ended.

From wireframes to a working app

The first build turned the wireframes into a React app on Supabase, and the second version was a rebuild that I treated more like a production system. It has a React 18 front end with React Router and TanStack Query, a single Hono API on Node with Supabase Postgres for data and storage, Firebase Auth for sign-in, push notifications, a service worker so it installs like a native app, and a Claude-powered button that drafts a listing description from a few notes. Moving from the first version's key-value storage to a relational schema let me push the important rules down into the database, so for example completing a trade is a single Postgres function that closes the listing and hands ownership to the buyer in one step.

Why a third version

The full-stack app is the real thing, but it needs a Vercel deployment, a database, Firebase and API keys to stay up, and that's a lot to keep running just so someone can click through a portfolio piece. I wanted a version that lives on my own site, costs nothing to host, and can't go down because a free tier expired, so I rebuilt it for GitHub Pages, which only serves static files.

The approach I took was to keep every screen from the full-stack version and replace only the layer underneath. The app talks to the same API class it always did, with the same method names and response shapes, but instead of making HTTP calls that class now answers from a small database stored in the browser. The rules the server used to enforce came along with it, so you still can't make an offer on your own listing, only the seller can accept, you can only rate a trade you were part of and only once, and completing a trade still moves the listing to the buyer.

Making a one-person marketplace feel alive

The hardest part wasn't technical. A marketplace demo where nobody ever answers is a dead end, so the seeded neighbors act on a short delay. If you make an offer the seller accepts it a few seconds later and messages you about pickup, if you ask a question in the chat you get a reply, if you list something a neighbor makes you an offer, and once a trade is done they rate you back. Each of those actions is queued with a time, so it still happens if you switch tabs or reload, and the screens refresh on their own when it lands. That way someone can walk through the whole loop, from listing to offer to chat to rating, in about a minute.

Accessibility and security

I ran axe-core against Section 508 and WCAG 2.x A and AA rules on every screen at phone and desktop sizes, and it turned up a few things that had carried over from the full-stack version, mainly white text on the light green ZIP badges that fell short of contrast, an unlabeled photo button, and scrollable areas that a keyboard couldn't reach. Those are fixed here, and the same fixes are worth carrying back to the full-stack version.

On the security side the page ships a strict Content Security Policy that only allows scripts from my own site, the fonts are self-hosted so there are no calls to Google, and the tests confirm that a whole session talks to nothing but this site and the photo CDN. Script typed into a listing or a chat message shows up as plain text and never runs, uploads are limited to real image types, and the service worker is scoped to this folder so it can't affect the rest of my site.

Testing

The 17 tests run in a real browser against the production build, served from /share-crops/ the same way GitHub Pages serves it. They walk through a full trade as a buyer and as a seller, sign-up and sign-in, creating a community, reloads and resetting the demo, along with the accessibility and security checks above, and the deploy won't go out if any of them fail.

What's next
